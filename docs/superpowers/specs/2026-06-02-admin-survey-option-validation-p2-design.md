# 관리자 설문 옵션 검증 P2 설계

작성일: 2026-06-02

## 목표

설문 문항 옵션의 무결성을 저장 시점과 제출 시점 양쪽에서 검증한다. 관리자가 객관식 문항을 옵션 없이 저장하거나 같은 라벨을 중복 입력하는 것을 막고, 사용자가 필수 객관식 문항을 선택하지 않고 제출하는 것을 서버에서 차단한다. P1에서 비범위로 미뤘던 옵션 검증과 필수 객관식 최소 선택 검증을 함께 처리한다.

## 현재 상태

- 관리자 저장은 `SAAdminSurveyController.saveSurvey()`에서 `@Valid` + `BindingResult`로 bean validation만 수행한다. `@NotBlank` 수준(title, label, optionLabel)만 검사한다.
- 의미 검증은 없다. 객관식 문항을 옵션 0개로 저장해도, 같은 라벨을 여러 번 넣어도 그대로 insert된다.
- `SASurveyService.insertChildren()`은 `source.normalizedOptions()`를 받아 검증 없이 옵션을 저장한다. `optionValue`가 비면 `optionLabel`을 그대로 쓴다.
- 공개 제출 `SASurveySubmitService.submit()`(P1)은 필수 객관식 최소 선택을 서버에서 검증하지 않는다. 주관식 `required`는 브라우저 HTML 검증에만 의존한다.
- 체크박스 그룹에는 HTML `required`를 걸지 않으므로(P1 결정) 필수 체크박스의 최소 선택은 현재 어디에서도 강제되지 않는다.

## 선택한 방향

검증을 저장 시점과 제출 시점 두 곳에 모두 둔다. 저장 검증은 데이터가 들어올 때 막는 1차 방어선이고, 제출 검증은 기존 설문이나 비정상 입력에 대한 안전망이다.

- 저장 검증은 기존 `BindingResult` 흐름을 재사용한다. 의미 규칙 위반을 `bindingResult.rejectValue()`로 등록하면 `saveSurvey()`가 이미 가진 "오류 시 `admin/survey/detail` 재표시" 경로를 그대로 탄다.
- 제출 검증은 `SASurveySubmitService`가 답변을 저장하기 전에 수행한다. 위반이 있으면 저장하지 않고 작성 화면을 오류와 함께 다시 보여준다.

### 대안 비교

1. bean validation 애너테이션만으로 처리한다.
   - 장점은 선언적이라 코드가 짧다.
   - 단점은 "객관식이면 옵션 1개 이상", "라벨 중복 금지" 같은 문항 간 교차 규칙을 애너테이션으로 표현하기 어렵다.

2. 저장은 서비스/컨트롤러의 명시적 검증 메서드로, 제출은 서비스 검증으로 처리한다.
   - 장점은 교차 규칙을 그대로 코드로 표현할 수 있고, 기존 오류 렌더링 경로를 재사용한다.
   - 단점은 검증 코드가 늘어난다.

3. 클라이언트 JavaScript에서만 막는다.
   - 장점은 즉시 피드백이 된다.
   - 단점은 서버 무결성을 보장하지 못한다. 기존 데이터나 직접 호출을 막을 수 없다.

권장안은 2번이다. 클라이언트 검증은 보조로 둘 수 있으나 P2의 기준은 서버 검증이다.

## 검증 규칙

### 저장 검증 (관리자)

객관식(`objective`) 문항에만 옵션 규칙을 적용한다. 주관식(`subjective`)은 옵션을 저장하지 않으므로 옵션 검증 대상이 아니다.

- 객관식 문항은 옵션이 **최소 1개** 있어야 한다. 0개면 거부한다.
- 같은 문항 안에서 옵션 **라벨 중복**을 금지한다. 공백을 trim한 뒤 비교한다.
- 옵션 개수 상한은 두지 않는다.
- 빈 라벨(공백만 있는 옵션)은 옵션으로 치지 않는다. 빈 라벨을 제거한 뒤 위 규칙을 적용한다.
- `optionValue` 정책은 기존 동작을 유지한다. 요청에 `optionValue`가 있으면 그대로 쓰고, 비어 있으면 `optionLabel`로 채운다(현재 `insertChildren()` 동작). P2는 value를 라벨로 강제 덮어쓰지 않고, value/label 불일치를 거부하지도 않는다.
- 따라서 value 유일성은 라벨 유일성으로 갈음한다. 라벨이 유일하고 value를 비워 두면 value도 유일하다. value를 직접 넣어 충돌시키는 경우의 검증은 비범위다.

검증 시점은 `normalizedOptions()`로 옵션을 정규화한 직후, insert 전이다. 위반은 해당 문항/옵션을 가리키는 메시지로 `BindingResult`에 등록한다.

### 제출 검증 (사용자)

- `required`(필수)인 객관식 문항은 최소 1개 값이 제출되어야 한다. 체크박스를 포함한 모든 객관식 필수 문항에 적용한다.
- `required`인 주관식 문항은 빈 값이 아닌 값이 제출되어야 한다. 브라우저 검증을 우회한 빈 제출을 서버에서 한 번 더 막는다.
- 비필수 문항은 값이 없어도 통과한다. P1대로 답변 row를 만들지 않는다.
- 위반이 하나라도 있으면 어떤 답변도 저장하지 않고 작성 화면(`client/survey/form`)을 오류 메시지와 함께 다시 보여준다.

#### 값 개수와 공백 처리

- 제출값은 검증 전에 trim하고, 빈 문자열은 제거한다. 그 뒤 남은 값 개수로 응답 여부를 판단한다.
- "빈 값"의 기준은 `null`, 빈 문자열, 공백 문자열을 모두 포함한다. 셋 다 미응답으로 본다.
- `select`, `radio`는 값이 0개 또는 1개다. 같은 키로 2개 이상이 오면 비정상 입력으로 보고 첫 번째 값만 사용한다(P1 동작 유지). 필수 검증은 trim 후 값이 1개 있는지로 판단한다.
- `checkbox`는 trim 후 남은 값이 1개 이상이면 응답한 것으로 본다.
- `[""]`처럼 빈 값만 담긴 배열은 trim·제거 후 0개가 되어 미응답으로 처리한다.

#### 제출 실패 재표시 경로

- 현재 `SAPublicSurveyController.submit()`은 성공 후 `redirect:/surveys/thanks.do`만 있고 실패 경로가 없다. P2에서 검증 실패 경로를 추가한다.
- 검증은 저장 전에 수행한다. 위치는 `SASurveySubmitService`의 검증 메서드로 두고, 위반 목록(문항 `fieldKey` → 메시지)을 반환하거나 전용 예외로 던진다.
- 컨트롤러는 위반이 있으면 저장을 호출하지 않는다. `detail`과 동일하게 `surveyService.findSurvey(surveyUid)`로 설문을 다시 로드해 `survey` 모델에 넣고, 위반 맵을 `errors` 같은 모델 속성으로 추가한 뒤 `client/survey/form`을 반환한다.
- 제출자가 입력한 값을 화면에 되살리는 것은 P2 필수가 아니다. 우선은 오류 메시지 노출과 재작성을 보장한다. 입력값 보존은 필요하면 후속 과제로 둔다.

### 오류 메시지

- 저장. "객관식 문항에는 보기를 1개 이상 입력해야 합니다.", "보기 라벨이 중복되었습니다." 수준의 한글 메시지를 문항 위치와 함께 노출한다.
- 제출. "필수 문항에 응답해 주세요."를 해당 문항 옆에 노출한다.

- `src/main/java/com/reven/project/admin/sa/SAAdminSurveyController.java` 또는 `src/main/java/com/reven/project/service/sa/SASurveyService.java`. 저장 검증 로직과 `BindingResult` 등록.
- `src/main/java/com/reven/project/service/sa/SASurveySubmitService.java`. 제출 검증과 위반 시 저장 중단.

- `src/main/resources/templates/admin/survey/detail.html`. 저장 오류 메시지 표시.

### 필요하면 같이 보는 파일

- `src/main/java/com/reven/project/service/sa/dto/SASurveyDto.java`. 검증 결과 전달용 구조가 필요하면 보조 추가.
- `src/main/resources/static/admin/js/survey-field-editor.js`. 클라이언트 보조 검증을 붙일 경우.

## 비범위

- 옵션 개수 상한 제한은 두지 않는다.
- `optionValue` 자체의 중복 검증은 라벨 검증으로 갈음하고 별도로 하지 않는다.
- 문항 순서 변경은 P4다.
- 미리보기는 P5다.
- 설문 복사는 P7이다.
- 응답 통계와 집계는 P8이다.
- 클라이언트 즉시 검증(JavaScript)은 선택 사항이며 서버 검증을 대체하지 않는다.

## 테스트 기준

### 저장 검증

- 객관식 문항을 옵션 0개로 저장하면 거부되고 작성 화면이 오류와 함께 다시 표시된다.
- 같은 문항에 동일 라벨을 두 번 입력하면 거부된다.
- 공백만 있는 옵션은 무시되고, 그 결과 옵션이 0개가 된 객관식 문항은 거부된다.
- 주관식 문항은 옵션이 없어도 정상 저장된다.
- 정상 객관식 문항(고유 라벨 1개 이상)은 기존대로 저장된다.

### 제출 검증

- 필수 객관식 문항을 선택하지 않고 제출하면 저장되지 않고 작성 화면이 다시 표시된다.
- 필수 체크박스 문항을 하나도 체크하지 않고 제출하면 거부된다.
- 필수 주관식 문항을 빈 값으로 제출하면 거부된다.
- 비필수 문항을 비워 제출하면 통과하고, 해당 문항 답변 row는 생성되지 않는다.
- 모든 필수 문항을 채운 정상 제출은 P1대로 저장된다.

### 회귀 기준

- 기존 정상 설문의 저장과 제출 흐름은 영향을 받지 않는다.
- P1의 객관식/주관식 렌더링과 다중값 저장 동작은 그대로 유지된다.

## 완료 기준

- 옵션 없는 객관식 문항과 라벨 중복 문항이 저장되지 않는다.
- 필수 객관식 문항을 선택하지 않은 제출이 서버에서 차단된다.
- 위반 시 사용자가 어떤 문항이 문제인지 화면에서 확인할 수 있다.
- 기존 정상 흐름과 P1 동작이 깨지지 않는다.

## 검토 의견

- (해결) 제출 실패 재표시 경로. §제출 검증 > 제출 실패 재표시 경로에 정의했다. 검증은 `SASurveySubmitService`가 저장 전에 수행하고, 위반 시 컨트롤러가 설문을 다시 로드해 `survey`와 `errors`를 모델에 넣고 `client/survey/form`을 반환한다.
- (해결) `answers[fieldKey]` 값 개수와 공백 처리. §제출 검증 > 값 개수와 공백 처리에 정의했다. trim 후 빈 값 제거, `select`/`radio`는 0~1개(2개 이상이면 첫 값만), `checkbox`는 1개 이상, `[""]`는 미응답으로 본다.
- (해결) `optionValue` 정책. §저장 검증에 명시했다. 요청 value가 있으면 그대로, 없으면 라벨로 채운다. 라벨로 강제 덮어쓰거나 불일치를 거부하지 않는다.
- (해결) `required` 주관식 빈 값 기준. §제출 검증 > 값 개수와 공백 처리에서 `null`, 빈 문자열, 공백 문자열을 모두 미응답으로 정의했다.
