# AI News 수집 방식 견적

## 배경

현재 프로젝트의 AI News는 이미 관리자 목록, 편집, 삭제, 크롤링 인입 경로가 있다.
외부 자동화가 JSON을 만들어 주는 구조와, 프로젝트 내부에서 직접 크롤링하는 구조는 작업 범위가 다르다.
이 문서는 두 방식의 범위와 대략적인 작업량을 분리해서 정리한 견적 문서다.

## 전제

- 현재 프로젝트에는 레거시 JSON을 읽어 DB에 반영하는 import 경로가 있다.
- 외부 Codex 자동화는 JSON 생산자 역할을 하고, Spring Boot는 소비자 역할을 맡는다.
- "배치"는 앱이 정해진 시각에 JSON import만 수행하는 방식이다.
- "인앱 크롤링"은 앱이 직접 원문 페이지나 API를 가져와 파싱하고 저장하는 방식이다.
- 관리자 화면과 DB 저장 구조는 이미 존재하므로, 새 작업의 대부분은 수집 계층에 집중된다.

## 옵션 1. 배치형

배치형은 가장 작은 범위다.
이미 만들어진 JSON을 매일 정해진 시각에 최대 5건씩 import하고, 성공 여부와 실행 이력을 남기는 수준이다.

### 포함 작업

- `@Scheduled` 기반 cron 등록.
- 최대 5건 제한 설정 분리.
- 중복 실행 방지.
- 마지막 실행 시각과 성공/실패 건수 기록.
- 기존 JSON import 서비스 재사용.

### 예상 작업량

- 0.5일에서 1.5일 정도.
- 현재 `crawlLegacyJsonFiles()` 같은 import 경로가 이미 있으므로, 새 수집 로직을 거의 만들지 않는 전제다.

### 리스크

- 다중 인스턴스 운영이면 중복 실행 방지가 필요하다.
- JSON 생성 실패와 import 실패를 구분해서 기록해야 한다.
- 배치 시간대와 수동 크롤링 버튼이 겹치면 동일 파일 재처리를 막아야 한다.

## 옵션 2. 인앱 크롤링형

인앱 크롤링형은 별도 서브시스템에 가깝다.
프로젝트가 직접 원문 소스에 접속해 목록 페이지와 상세 페이지를 읽고, 필요한 데이터를 파싱해 DB에 넣어야 한다.

### 포함 작업

- 수집 대상 소스 정의.
- 목록 페이지 파서와 상세 페이지 파서.
- 페이지네이션 처리.
- 중복 제거 규칙.
- 실패 재시도와 예외 기록.
- 소스별 HTML 구조 변화 대응.
- 수집 결과 정규화와 저장.
- 운영자 확인용 로그 또는 이력 화면.

### 예상 작업량

- 단일 고정 소스 기준으로 3일에서 5일 정도.
- 운영 가능한 형태로 만들면 1주에서 2주 이상.
- 수집 소스가 여러 개면 소스마다 추가 작업이 붙는다.

### 리스크

- 외부 사이트 구조가 바뀌면 파서가 쉽게 깨진다.
- rate limit, 차단, 로그인, anti-bot 대응이 필요할 수 있다.
- 수집 실패 원인을 추적할 운영 로그 없이는 유지보수가 어렵다.
- 소스별 파싱 규칙이 늘수록 테스트 비용이 커진다.

## 비교

| 항목 | 배치형 | 인앱 크롤링형 |
|------|------|------|
| 목적 | 이미 생성된 JSON을 자동 반영 | 원문 소스를 직접 수집 |
| 범위 | 스케줄러, 제한값, 로그, 중복 방지 | 파서, 페이지네이션, 재시도, 중복 제거, 운영 로그 |
| 예상 작업량 | 0.5일 ~ 1.5일 | 3일 ~ 5일, 운영형은 1주 ~ 2주+ |
| 유지보수 난이도 | 낮음 | 높음 |
| 추천도 | 높음 | 조건부 |

## 결론

현재 프로젝트 맥락에서는 배치형이 가장 적은 비용으로 붙는 방식이다.
이미 JSON 생산 주체가 외부에 있고, 프로젝트는 import와 저장, UI 책임만 가지는 구조가 더 단순하다.

인앱 크롤링은 "JSON 생산까지 프로젝트 안에서 모두 책임지겠다"는 요구가 확정될 때 선택하는 편이 맞다.
그 경우는 단순 배치가 아니라 별도 크롤러 서브시스템으로 보는 것이 맞다.

1차 권장안은 배치형이고, 인앱 크롤링형은 이후 확정 요구가 생겼을 때 별도 단계로 분리하는 것이다.
